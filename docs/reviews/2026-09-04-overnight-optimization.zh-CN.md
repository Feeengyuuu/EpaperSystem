# 架构优化与实机夜间日志分析

分析日期：2026-09-04。夜间窗口：2026-09-03 18:00 至 2026-09-04 09:00，设备时区 America/Los_Angeles（PDT，UTC−07:00）。

## 结论

系统在该窗口内持续完成写屏，但数据刷新和主题恢复存在可以复现的调度缺陷。本次优化同时处理结构问题与日志证实的问题：抽出刷新计划、明确插件生命周期和执行上下文、隔离 F1 领域逻辑，并修复车辆无效主题补图及 Weather 资源恢复机会丢失。不会把缓存可显示当成数据已更新。

## 证据范围与限制

- 从实机 journal 导出 5294 条记录，覆盖 18:00:02 至 08:59:45；另取 09:00 至 12:50 的日志定位恢复时间。
- 按应用日志中的 WARNING/ERROR 标记计数，得到 91 条警告、6 条错误。不能只按 journal priority 筛选：Python 警告也被 journal 记为 priority 6。
- 夜间有三个正常 stop/start 边界，因此按 PID 分段。日志显示正常停启，不把这些边界推断为进程崩溃。
- 共发现 182 次驱动写屏开始、180 次 sleep 完成日志。缺少配对 sleep 的两次开始分别是 19:28:49 和 01:33:16，随后均紧邻服务停止边界；不能据此判定为硬件故障。日志证明驱动调用链，不能证明面板光学状态。
- DATA 的 started 日志是任务开始证据；Sports 的隔离区段也会重复出现该事件，不能把区段数当成完整数据刷新成功次数。
- 当前配置快照只证明采样时配置。夜间 Weather 日志明确普通门槛为 150 MB；通用后台缓存门槛 175 MB 是另一项配置，不能混用。
- 原始日志保留于本地 .tmp，提交的汇总不包含账号凭据、原始服务响应或个人位置。

## 已定位并修复的问题

### 1. 车辆页面反复执行不需要的主题缓存补齐

9 月 3 日 19:56、20:18，以及 9 月 4 日 07:17、07:27、07:47，Vehicle 的 THEME_CATCHUP 均因无法产生可正式缓存的图片失败。单次约 0.8–1.3 秒，不足以解释数分钟写屏延迟。

车辆已声明支持显示时本地重绘：它能读取源缓存，按当前时间更新离线时长和主题。陈旧／缺失数据产生的图像禁止晋升为正式缓存，这是正确的保护。但主题补齐调度仍要求这些图像成为正式缓存，形成无效重试。

修复在元数据筛选阶段跳过具有该能力的插件，避免消耗补图配额和再次记录尝试。车辆 DATA、当前页主题更新及轮播本地重绘保留；普通插件的主题补图继续执行。回归验证同时覆盖历史失败重试、无正式 PNG、日夜自动主题，以及陈旧／缺失源数据不改写 DATA 成功状态。

### 2. Weather 内存恢复后错失正常刷新机会

07:37:51 至 09:03:15，相邻 Weather DATA 开始时间相隔约 85 分 25 秒。日志中有资源退避和其他工作交错，不能把整个间隔都归因于单个原因。

两条具体链路可以由代码和回归测试共同证实：

- 08:13:39 的资源退避设置了约一分钟后的重试；08:14:03 内存已达 152.26 MB，却因为普通候选出现而结束 Weather 等待窗口。
- 08:38:09 可用内存 146.91 MB，重试时间设为 08:39:09；回收后超过 158 MB。08:38:14 仍先结束窗口并执行 SteamProfile，Weather 被自己的旧资源退避隐藏。

修复让已有等待窗口在恢复到普通门槛后执行恢复判断，即使此时有普通候选也不丢失该窗口的一次恢复机会。Weather 成功后，普通任务仍可随后入选。没有窗口时保持原有普通排序；门槛不足时继续让可执行的其他工作运行。

额外回归确认：窗口期间新增 provider 失败会结束该窗口，保留新的失败退避；不会借资源恢复绕过上游退避。已就绪轮播进入写屏保护窗口时，普通恢复和限次低余量尝试均不会重建被过滤的长任务；短任务仍可执行。SOFT 间距与执行时资源复查保持生效。

## 上游故障与资源保护

夜间还出现 NOAA DNS 失败、APOD scales 核心数据缺失、报纸源 403、部分图片下载失败、Steam Charts 浏览器超时后使用 PIL 回退，以及 Sports 隔离进程在低内存下主动退避。这些事件需要保留可观测性和新鲜度语义，不适合通过忽略异常或放宽资源门槛消除。

历史 last_error 也不能直接当作当前故障：APOD、车辆状态在后续有成功记录。部署前 /readyz 一度为 degraded，12:56 的重新采样已恢复 ready；这属于发布前状态变化，不能记成本次优化的成效。

## 结构优化

| 边界 | 改动与作用 |
| --- | --- |
| 刷新计划 | 提取纯计划模块，输入不可变候选与资源事实，输出命令计划；IO、事务和执行仍在宿主层 |
| 插件注册 | 应用持有统一 registry，惰性创建并发安全，每个应用独立实例，兼容入口转发到同一实现 |
| 执行上下文 | 显式传入取消、截止时间和实例身份；保留旧插件适配及最终事务校验 |
| Sports / F1 | 18 个 Jolpica 解析和选择函数移入纯领域模块，移除 F1 通配导入；其余体育适配逐步迁移 |
| 测试命名空间 | 统一安装时导入路径，消除 src.* 与 runtime/plugins 重复模块身份 |
| CI | 每个 shell 文件单独语法检查；新增架构依赖、规模和 mypy 检查，独立验证车辆 Worker |

设计与边界说明见 [架构实施记录](../architecture/2026-09-04-optimization.md)。本次是受测试保护的分步拆分，仍保留大型调度宿主和其他 Sports 适配器，并未宣称完成全部技术债清理。

## 验收口径

发布准备中还核实并修复了现有 CI 问题：

- edbd9081 的完整测试先出现两个失败，随后约 9% 进度处停滞至 20 分钟上限，clean archive 未启动。两项测试改成独立矩阵任务，并在首次失败时输出结果、长时间无返回时输出调用栈；拆分任务本身不代替修复具体失败，最终仍需 Linux CI 通过。
- 运行锁中 Pillow 12.2.0、cryptography 49.0.0、pi-heif 1.2.0 被审计报告命中，更新至 12.3.0、50.0.1、1.3.0。开发锁中的 pip 更新至 26.2.1。重建哈希锁后，运行与开发依赖审计均无已知漏洞；其余锁定版本保持不变。变更依据见 [Pillow 安全修复](https://pillow.readthedocs.io/en/stable/releasenotes/12.3.0.html)、[cryptography 变更记录](https://cryptography.io/en/stable/changelog/)、[pi-heif 发布元数据](https://pypi.org/project/pi-heif/1.3.0/) 与 [pip 发布元数据](https://pypi.org/project/pip/26.2.1/)。
- 新版本均有实机 aarch64 / Python 3.13 对应二进制包，已按锁文件哈希下载验证；发布仍需确认设备中的实际安装版本。
- 秘密扫描的五个历史命中经逐项核实：四项为可从公开测试参数复算的缓存哈希，一项为车辆气候字段允许集合。仅添加精确的提交／路径／规则／行号排除。候选发布历史扫描通过，未扩大规则或目录豁免。

针对修复的集成回归已通过 645 项。完整测试与 clean archive 必须在最终提交上通过，随后核对实机活动版本、Python 文件哈希、任务终态、数据新鲜度、当前图像和实际驱动写屏。完整结果另存部署验收记录；本报告的历史观察不能代替部署后的验证。
